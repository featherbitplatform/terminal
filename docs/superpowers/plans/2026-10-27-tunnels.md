# Tunnels Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Named SSH tunnels (local forward, remote forward, SOCKS5) defined per profile, started on demand or with the shell, shown and toggled in a searchable tunnels panel and the palette, reconnecting on their own with a configurable retry limit.

**Architecture:** Definitions live in `SshProfile.tunnels` (`fbterm-config`). The runtime lives in `fbterm-session::ssh::tunnel`: a tunnel task acquires the profile's shared `Arc<Connection>` from `SshPool` (keeping the connection open while the tunnel is on), runs the listener or remote forward, and reports state transitions over its own channel; a disconnect signal pushed from `ClientHandler::disconnected` drives reconnecting with backoff. The app keeps a `Tunnels` registry keyed by `(ProfileId, name)`, derives "with the shell" lifetimes from open panes, and renders the panel window, the tab-bar indicator and palette items.

**Tech Stack:** Rust 2024, russh 0.64.1 (`channel_open_direct_tcpip`, `tcpip_forward`, `cancel_tcpip_forward`, `Handler::server_channel_open_forwarded_tcpip`, `ChannelStream`), tokio (`TcpListener`, `copy_bidirectional`, `watch`, `mpsc`), iced 0.14.

**Spec:** `docs/superpowers/specs/2026-10-27-tunnels-design.md` (approved; refines `2026-10-23-featherbit-terminal-design.md` 5.3 and 5.7).

## Global Constraints

- In-process `russh` only; never the system `ssh`. Tunnels ride the profile's one shared connection and its jump chain.
- A remote program can never open, change or close a tunnel: unsolicited `forwarded-tcpip` channels are rejected unless they match a remote forward this app requested on that connection; hop connections reject them always.
- Default bind address `127.0.0.1`; a non-loopback bind is allowed only when typed explicitly and shows a warning in the profile editor: `Listens on {addr}: other machines can reach this tunnel.`
- Start modes: `on_demand` (default) and `with_shell`. A `with_shell` tunnel runs while at least one shell (tab or pane) of its profile is connected; it stops when the last one closes or disconnects. Switching it on by hand with no shell open makes that run on-demand.
- Reconnecting (on-demand tunnels, and with-shell tunnels switched on by hand): backoff 1, 2, 4, 8, 16 s, then every 30 s; at most `tunnel_max_retries` attempts (Settings, default `10`, range `0..=100`, 0 = no automatic retrying). Automatic attempts never prompt: a reconnect that needs the user fails at once with reason `needs your input`.
- States and exact labels: `Off`, `Starts with the shell`, `Starting`, `Up`, `Up · {n} connections` (`1 connection`), `Reconnecting (attempt {k} of {max})`, `Failed: {reason}`; plus the marker `Restart to apply` on a running tunnel whose definition changed.
- Failure notification (banner): `Tunnel "{name}" ({profile}) failed: {reason}`.
- Palette rows: `Tunnel: {profile} / {name}` with the state on the right; choosing a row toggles it.
- Panel window title `Tunnels · fbterm`; search placeholder `Search tunnels`; address line `localhost:5432 → db.internal:5432 via bastion` style (`{bind}:{port} → {host}:{port}` for local, `remote {bind}:{port} → {host}:{port}` for remote, `SOCKS {bind}:{port}` for SOCKS; `via {jump names joined by " → "}` when the profile has jumps).
- SOCKS: SOCKS5, CONNECT only, no authentication, hostnames resolved on the remote side; no UDP or BIND; other requests answered with the matching SOCKS5 error code.
- On relaunch nothing is restarted automatically except `with_shell` tunnels with their restored shells.
- Redraw contract: state transitions are events; connection counts coalesced to at most 4 updates per second per tunnel; backoff timers live in the tunnel task; no periodic subscription.
- No new `unsafe`; cross-platform; no emoji or em-dashes in product copy; never name another terminal application; secrets only in the keychain; Conventional Commits with no attribution of any kind.
- Gates per task: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`; live tasks also `FBTERM_TEST_SSH=1` live tests with Docker (`CLAUDE.md`); `cd website && npm run build` when docs change.

## Review Focus

1. The local port is already taken (e.g. a local Postgres on 5432): the tunnel fails with `Failed: port 5432 already in use` and a banner; nothing else breaks. Test in Task 3 (`bind_in_use_fails_with_reason`).
2. The laptop sleeps or switches network with an on-demand tunnel up and no shell: it shows `Reconnecting (attempt k of 10)` and comes back when the network does, or fails after 10 attempts. Test in Task 4 (`server_restart_reconnects_tunnel`, `retries_run_out_then_fail`).
3. A remote program on the server asks to open a forwarded channel to this machine without a matching remote forward: rejected, nothing connects locally. Test in Task 2 (`unsolicited_forwarded_channel_is_rejected`).
4. Two panes of the same profile with a `with_shell` tunnel: closing one keeps the tunnel up, closing the second stops it, and reconnecting a pane (Enter) starts it again. Test in Task 5 (`with_shell_follows_last_shell`).
5. Editing a running tunnel's port in the profile editor: the tunnel keeps running on the old port and shows `Restart to apply`; deleting it stops it. Test in Task 5 (`edit_marks_restart_to_apply`, `delete_stops_tunnel`).

### Task 3: Tunnel runtime: local, remote and SOCKS

**Files:**
- Create: `crates/fbterm-session/src/ssh/tunnel.rs`, `crates/fbterm-session/tests/ssh_tunnels.rs` (own copies of the live helpers), `.github/workflows/ci.yml` (run both live test files)

**Interfaces:**
- Consumes: Task 1 `TunnelDef`, `TunnelKind`; Task 2 `acquire`, `closed`, forwards registry, `NoPrompt`.
- Produces:
  - `pub struct TunnelKey { pub profile: ProfileId, pub name: String }` (Clone, Eq, Hash, Debug).
  - `pub enum TunnelState { Starting, Up { connections: usize }, Reconnecting { attempt: u32, max: u32 }, Failed(String), Off }` (Clone, PartialEq, Debug).
  - `pub type TunnelSink = mpsc::UnboundedSender<(TunnelKey, TunnelState)>`.
  - `pub struct TunnelHandle` with `pub fn stop(&self)` (Drop stops; stopping closes the listener, cancels a remote forward, ends live connections, releases the `Arc<Connection>`).
  - `pub fn start_tunnel(pool: Arc<SshPool>, store: ProfileStore, key: TunnelKey, def: TunnelDef, prompter: Arc<dyn Prompter>, retries: Arc<AtomicU32>, events: TunnelSink) -> TunnelHandle` (first attempt with the given prompter; the definition is snapshotted).
  - Local: bind `TcpListener` on `bind:port` (errors: `port {p} already in use`, `port {p} needs administrator rights`, else the OS message), each accept opens `channel_open_direct_tcpip(host, host_port, peer_ip, peer_port)` and `copy_bidirectional`; a failed channel open closes that one client connection and leaves the tunnel up.
  - Remote: `tcpip_forward(bind, port)` (denial: `server refused the forward: {reason}`), register in the forwards map, each forwarded channel connects a `TcpStream` to `host:host_port` and copies; `cancel_tcpip_forward` on stop.
  - SOCKS5: greeting (no-auth only, else `0xFF`), CONNECT with IPv4, IPv6 or domain (domain passed as-is to `channel_open_direct_tcpip`, never resolved locally), reply codes per RFC 1928 (`0x07` for other commands, `0x05`/`0x04` mapped from channel-open failures), then copy.
  - Connection counts reported coalesced (at most every 250 ms, and always on reaching 0).
