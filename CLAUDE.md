# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**featherbit terminal** (also *featherbiterminal*), binary `fbterm`: a native, SSH-first terminal emulator in Rust with an **iced** GUI. Built to stay fast and light with ~20 concurrent sessions (streaming logs, idle shells, AI-agent TUIs), with saved SSH profiles, jump hosts, a quick-launch palette, tabs and tiling, named tunnels, an SFTP file panel and encrypted profile export. Also a plain terminal for local shells.

Binding design: `docs/superpowers/specs/2026-10-23-featherbit-terminal-design.md`. Read it before any feature work; it records which decisions are the owner's and which are open builder's calls. Implementation plans go next to it under `docs/superpowers/plans/`.

## Rules specific to this repo

- **Describe the product only on its own terms.** Never name or compare to another terminal application anywhere committed to this repo: code, comments, docs, website, commit messages, PR text, this file.
- **Cross-platform code, macOS releases first.** Code must build and test on macOS, Linux and Windows (CI covers all three); platform-specific APIs only behind `cfg` with an alternative. Release artifacts are unsigned (macOS `.dmg` for Apple Silicon + Intel, Linux `.deb`/`.rpm`/`.tar.gz`, Windows `.msi`) until signing is decided.
- **Secrets never go in config files.** Passwords and key passphrases live in the system storage (macOS and Linux: a single OS-keychain item, a map keyed by profile id, via the `keyring` crate; Windows: the DPAPI-encrypted file `secrets.dpapi`) or in the `age`-encrypted vault `secrets.fbvault`, chosen by the `secret_storage` setting; config is TOML in the platform config dir.
- **No home-grown crypto.** Export archives (`.fbprofiles`) use `age` with a passphrase recipient. "Shared" exports strip passwords, passphrases and key paths.
- **Host keys:** `~/.ssh/known_hosts` shared with OpenSSH; trust-on-first-use prompt for unknown hosts; changed keys are refused, never auto-accepted.
- **Look and feel** follows the workspace design system v2 "Graphite" (`../design-system-v2/`, start at its `SKILL.md`): dark-first graphite, violet as the single accent, Geist Mono for real values, Lucide icons, no emoji or em-dashes in product copy.

## Architecture (from the design)

- **Emulation:** `feathercritty` (our Apache-2.0 fork of the upstream emulation crate, [github.com/featherbitplatform/feathercritty](https://github.com/featherbitplatform/feathercritty)) owns parsing, grid and scrollback per session. Local shells via `portable-pty`.
- **Rendering:** custom iced widget drawing from a glyph atlas with damage tracking; invisible tabs do no render work. If iced primitives are too slow, the approved fallback is a raw wgpu renderer for the grid inside the iced window — iced stays for all chrome. Switching GUI toolkit is not an option without the owner.
- **SSH:** in-process `russh`, never shelling out to system `ssh`. Auth in scope: password, private key (± passphrase), ssh-agent; 2FA, FIDO keys, certificates and agent forwarding are deferred.
- **Connection model:** one SSH connection per profile, shared like ControlMaster. Every tab/pane is a shell channel on it; the file panel (SFTP via `russh-sftp`) and tunnels are further channels. Tunnels belong to the connection, not to a tab: `with-shell` tunnels start when the profile's first shell connects and stop with its last, on-demand tunnels may open a shell-less background connection, and the connection closes only when its last channel does.
- **Jump hosts:** a profile's jump chain references other saved profiles; each hop is SSH over a `direct-tcpip` channel from the previous hop, authenticated with that hop's own profile.
- **Runtime:** one process, tokio for I/O, one task per session feeding its terminal; background sessions keep parsing but never render. Multi-window (iced daemon mode); windows, tabs and pane layout restore on relaunch, reconnecting as built: every pane of each window's visible tab at once, background tabs on first show.
- **Palette:** Cmd+Shift+P (Ctrl+Shift+P elsewhere), application-scoped, fuzzy (`nucleo`) over profiles first, then tunnels (choosing one switches it on or off), then app actions.
- **Shortcuts:** actions, chords, per-platform defaults and the binding table are data in `fbterm-config/src/keys.rs`; the user's overrides are the `[keys]` table of `settings.toml`. The app keeps one `Bindings` (`App::bindings`, rebuilt when settings apply) and matches presses against it in `keys.rs`/`shortcuts.rs`; tooltips, the palette and the Settings window's Keyboard section read the same table, so never hardcode a chord label.

## Conventions

- **Gitflow:** `main` holds tagged releases (`vX.Y.Z`) only; `develop` is the integration branch; work on `feature/<name>` off `develop`; `release/X.Y.Z` and `hotfix/<name>` as in the gateway repo.
- **Conventional Commits** (`feat:`, `fix:`, `docs:`, `ci:`, `chore:`, `refactor:`, `test:`, optional scope). Do not add a `Co-Authored-By` trailer.
- **Semantic versioning**, released like the gateway: `release/X.Y.Z` off `develop` (version bump in `Cargo.toml` there), merged into `main` with an annotated `vX.Y.Z` tag, then merged back into `develop`. The `v*` tag triggers the release workflow.
- Docs website: Docusaurus in `website/`, deployed to `https://featherbitplatform.github.io/terminal/` by `.github/workflows/docs.yml` — same pattern as `../gateway/website`.
- CI gates: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `cargo deny check`, plus the security scans in `.github/workflows/security.yml` (semgrep, cargo-deny, grype, gitleaks over the full history, npm audit of `website/`; also weekly on `main`). Their configs live at the repo root (`.semgrepignore`, `.gitleaks.toml`, `.grype.yaml`, `deny.toml`, `website/audit-ci.jsonc`); every ignore carries a one-line reason. Releases attach CycloneDX SBOMs (`fbterm-<version>.cdx.json`, `fbterm-docs-<version>.cdx.json`, syft pinned in `release.yml` and `dev/sast.sh`).

### Debug aids (environment variables)

- Always available: `FBTERM_CONFIG_DIR=<dir>` (use this directory instead of the real config), `FBTERM_SECRETS=memory` (never touch the OS keychain), and the release-build measurement flags `--perf-tabs <N>` (or `--perf-panes <N>`: one tab with N panes) `--perf-cmd <cmd> [--perf-exit-after <secs>] [--perf-close-after <secs>]` (the last closes every tab but the active one).
- Always available, for keyboard reports: `FBTERM_LOG_KEYS=1` (read once at startup, `key_log.rs`) logs at INFO, while the Settings window records a shortcut and only then, one line per keyboard event (`KeyPressed`, `KeyReleased`, `ModifiersChanged`) in any window: key, modified key, physical key, location, modifiers, repeat, the typed text and character keys (recording window only; elsewhere named keys and physical keys) and whether it was captured. Each event is logged by the window-level listener (`listener`: did the window get it at all, and did a widget capture it) and by each `Shortcuts` wrapper it reaches (`shortcuts`: captured before the wrapper saw it). Windows release builds have no console, so send stderr to a file from PowerShell: `$env:FBTERM_LOG_KEYS=1; Start-Process "C:\Program Files\featherbit terminal\fbterm.exe" -RedirectStandardError "$env:TEMP\fbterm-keys.log" -Wait`, record the shortcut in Settings, quit fbterm, then read `$env:TEMP\fbterm-keys.log`.
- Debug builds only (ignored in release): `FBTERM_OPEN_TABS=<profile>,<profile>`, `FBTERM_SPLITS=<layout>` (the first tab as split panes of these profiles: `|` side by side, `/` stacked, binding left to right, e.g. `A|B/C`), `FBTERM_PALETTE_QUERY=<text>`, `FBTERM_SCREENSHOT=<path.png>` (capture the first window and exit), `FBTERM_SCREENSHOT_WINDOW=editor|settings|schemes|tunnels|archive`, `FBTERM_OPEN_EDITOR=<profile>`, `FBTERM_OPEN_SETTINGS=1` (`secrets`: scrolled to the Saved secrets section), `FBTERM_DEMO_VAULT=1` (with `FBTERM_SECRETS=memory`: makes the in-memory backend's temporary vault, main password `demo`, so Settings shows `Reset vault`; a screenshot waits for it), `FBTERM_OPEN_SCHEMES=1` (the Color schemes window; any other value selects the scheme of that name), `FBTERM_OPEN_TUNNELS=1` (the Tunnels window), `FBTERM_OPEN_ARCHIVE=export|import` (the export and import window in that mode; with `FBTERM_DEMO_ARCHIVE=1` export starts with jump hosts unchecked and key files on, and import shows a sample archive built in memory, its key folder in the temporary folder), `FBTERM_DEMO_FILES=<folder>:<item>,<item>,...` (the first window's file panel open on a sample listing served for every SSH pane and folder, connected or not, never touching the network, with a sample transfer queue (a running and a finished download of the first files and a failed in-place upload; `Download`, `Upload…` and `Retry` there add rows that stay at their start); an item is `name`, `name/` for a folder or `name -> target` for a link (target ending in `/`: a folder), optionally followed by `|<bytes>|<YYYY-MM-DDTHH:MM>`), `FBTERM_DEMO_UPLOAD=<name>,<name>` (with `FBTERM_DEMO_FILES`: upload these names into the first listing shown, raising the clash dialog for names it has), `FBTERM_DEMO_PROMPT=hostkey|password|keyfile|changed|unlock|setpassword` (`setpassword` only with `FBTERM_SECRETS=memory`), `FBTERM_DEMO_TOOLTIP=new|profiles|tunnels|settings|close` (keep that tab-bar tooltip showing), `FBTERM_FIND=<text>` / `FBTERM_FIND_ALL=<text>` (open the active tab's find bar or the find-in-all-tabs box with that query, about a second after startup), `FBTERM_SCALE=<factor>` (extra UI scale on top of the OS's, e.g. `0.625` on a 2x screen for a fractional 1.25), `FBTERM_DEMO_CHROME=windows|linux[:<button-layout>]` (draw that system's window controls on any system, Linux with an optional GNOME `button-layout` value, e.g. `linux:close,minimize,maximize:`). Runs with `FBTERM_OPEN_TABS`, `FBTERM_SPLITS` or `FBTERM_SCREENSHOT` never write `state.toml`.
- Always on, in the config dir (`crash.rs`, paths in `fbterm-config/src/paths.rs`): `fbterm.log` gets every log line stderr shows (INFO, no colors), and each start first moves the last run's log to `fbterm.previous.log`. A panic (hook installed first thing in `main`, after `--version`; the default hook still prints to stderr) or `daemon.run()` failing appends a report (UTC time, version, OS and arch, thread, message and location, backtrace) to `crash.log`, moved to `crash.previous.log` before an append once it is over 256 KiB; a failed start also shows a message box on Windows. Each report creates the empty marker `crash.pending`, which the next launch removes, showing `fbterm ran into an error last time. The report is in <crash.log>.` once in the window banner; runs that never write `state.toml` leave the marker alone.
- Rule for agents: look at the app only through its own-window screenshots (`FBTERM_SCREENSHOT`), never full-screen capture. Combine with `FBTERM_CONFIG_DIR` and `FBTERM_SECRETS=memory` so a run cannot touch real profiles or secrets.

## Gotchas learned

- Windows CI clippy fails on imports and helpers used only by `#[cfg(unix)]` tests; gate them with the same `cfg`.
- Linux packages are built in an `almalinux:9` container (glibc 2.34, RHEL 9's), not Debian 12: a Debian 12 build links `hypotf@GLIBC_2.35` and the `.rpm` then refuses to install on RHEL 9. `dev/package-linux.sh` refuses a binary that needs a glibc symbol newer than 2.34. The binary links only glibc and libgcc; winit, wgpu and rfd open the rest at run time (list in the `[package.metadata.deb]` comment of `crates/fbterm/Cargo.toml`); recheck with `strings` on the release binary after dependency upgrades.
- Windows release builds are GUI-subsystem programs (`windows_subsystem` in `main.rs`, release only), so no console window opens beside the app; their stdout reaches only a pipe or file (`fbterm --version | more`), and any child process they start needs `CREATE_NO_WINDOW` or it flashes a console. `build.rs` embeds the icon and version information with `winresource` (Windows hosts only). The `.msi` (`crates/fbterm/wix/main.wxs`) keeps one UpgradeCode forever; never change it.
- Window chrome is `Chrome` in `crates/fbterm/src/chrome.rs`: `Unified` on macOS (never changed), `Drawn` on Windows and, by default, Linux (no OS decorations; the tab bar holds drawn controls, moves and resizes through iced's `drag_window`/`drag_resize`), `Native` only on Linux. It lives in a switchable `ChromeCell`: the `window_decorations` setting and the fallback (`move_watch.rs`: a move or resize the desktop ignores, detected once per session, sets `chrome_fell_back` and shows `FALLBACK_NOTICE`; the setting itself stays `"fbterm"`) toggle decorations on open windows. Never treat an ordinary click as a move request, or the fallback fires falsely. The Settings blur row asks `chrome::blur_here()` (Windows build >= 22621 via `reg query`, Linux Wayland + KDE, macOS always).
- `hdiutil create` fails locally on macOS 27 ("Resource busy"); `dev/package-macos.sh` falls back to `diskutil image create` locally, CI uses `hdiutil` only.
- Redraw contract: call `take_dirty` before locking the terminal to draw; hidden tabs, and every tab of a window that cannot be seen (`visibility.rs`), leave `Dirty` pending until they are shown. Every message redraws every window, so output `Dirty` is paced before it reaches the update loop (`pacing.rs`, at most `max_fps` per second: the setting, default `OUTPUT_FPS` = 60, or the fastest display with `"display"` via `display_rate.rs`; read live from the shared `OutputRate`); never add a periodic subscription or redraw loop that keeps running without new output or input (debug aids aside).
- `feathercritty` is a git dependency pinned by `rev` in the root `Cargo.toml` (its changes from upstream are listed in its README; `deny.toml` allows git sources from `github.com/featherbitplatform` only). To change emulation code: commit in the feathercritty repo (`../feathercritty`, Conventional Commits, notice line at the top of each file it modifies), push, wait for its CI, then bump the `rev` here and run the checks. For local development, point Cargo at the working copy with a `[patch."https://github.com/featherbitplatform/feathercritty"]` entry `feathercritty = { path = "../feathercritty" }` in the root `Cargo.toml`; never commit it.
- feathercritty stores scrollback in a compact byte form, so `grid[...]` indexing is screen-only: use `grid.screen()[...]` for the visible rows and `grid.screen_mut()` to write them. History rows are read through `RowReader`, `Grid::cell`, `Grid::wraps` and `Grid::is_clear` (see the feathercritty README, "Compact history"); never index a history line directly.
- Search positions are `StablePoint`s (`fbterm-term/src/search.rs`): stable line = feathercritty's `Grid::scrolled_lines()` + grid line, unchanged while output scrolls; a resize (reflow) or a screen switch invalidates them, so the find bar searches again then.
- The tab bar paints its background around the active tab only (`BarBackground` in `window.rs`: rectangles plus concave top-corner pieces and bottom flares drawn as clipped disc and ring quads, all in whole physical pixels from `App::physical_scale`; it also paints the inactive tabs' hover and tint), so a translucent bar never lies under the active tab; anything drawn behind it would double the alpha. Tab colors (stripe or whole-tab tint, contrast-picked text) come from `tab_look.rs`.
- Tab export (`fbterm-term/src/export.rs`, `fbterm/src/export.rs`) streams the history on the blocking pool in 1000-row chunks, locking the terminal per chunk and addressing rows by stable line (like search), into a temporary file renamed at the end; with the alternate screen up it reads the normal grid through feathercritty's `Term::inactive_grid()`.
- A session can continue into an existing `SharedTerminal` (`spawn_local_into`, `open_shell_into`), which is how reconnect keeps scrollback.
- Freed scrollback goes back to the OS through `memory::release_freed()` (macOS `malloc_zone_pressure_relief`, glibc `malloc_trim`, nothing elsewhere; at most once per 5 s, on the blocking pool). Only user actions call it (closing a tab or window, requested when the closed session task reports `SessionEvent::Released` after dropping its terminal, which only a user close triggers; lowering `scrollback_lines`); a program's own history clear (`CSI 3 J`, `RIS`) must never, because remote programs cause no host work. Lowering `scrollback_lines` applies to every open tab through `Terminal::set_scrollback`; `apply_settings` takes a `SettingsSource` (`File` sets the settings notice, `Window` does not).
- Tunnels share the pooled SSH connection of their profile (`SshPool::acquire`); the tunnel runtime claims its forward exclusively (`claim_forward`), and a restart must `stop_and_wait` first so the port is released. The client handler (`ssh/mod.rs`) refuses every server-opened channel unless it is a `forwarded-tcpip` for a remote forward registered on that connection, and always on hop connections: a remote program must never open, change or close a tunnel. A pooled connection is handed out only on the profile's current route (the SSH settings of the profile and its jump chain), so an edit makes the next caller dial afresh while running tunnels keep the old one. The raw remote-forward calls on `Connection` exist only with the crate's `test-support` feature, for the live tests.
- File panel transfers hold their own `Arc<Sftp>` and belong to the connection, not to a panel or window: hiding the panel never cancels them, and the app never cancels them implicitly (only the user's `Cancel`, or `Cancel transfers and close` in the close or quit confirmation in `prompts.rs`/`file_panel/queue.rs`). Nothing is ever written half-done under a real name: downloads and uploads go to `.<name>.fbterm-part` and are renamed on completion (removed on cancel or failure); a Replace upload uses the part file plus `posix-rename@openssh.com` and falls back to an in-place write (`Replaced in place`, `File may be incomplete.` on failure). Two downloads never share a destination (`same_destination`, case-insensitive), and `Download` (`DownloadMode::FreeName`) never replaces a file that appeared meanwhile (hard link to the final name, else the next free name). Every upload starts through `launch_job` in `queue.rs`, which refuses a second upload of a name already uploading into that folder. Server names use one unsafe-character set on both sides (`transfer::is_unsafe_char`: shown as `?`, written locally as `_`). A remote program must never start a transfer or open the panel.
- Color scheme resolution: profile override, then global `color_scheme`, then Graphite, always through `App::scheme_for` (never read a pane's colors elsewhere). After scheme files change call `App::reload_schemes`; after a setting or profile change `schemes_moved` recolors the affected panes (`reapply_schemes`). Scheme notices (unreadable files, missing ids) go to the window banner via `refresh_scheme_notices`, once per distinct line. Pane accent borders draw only in tabs with more than one pane.

- Shared archives are stripped by construction: `archive_build::shared_copy` destructures the profile and its SSH and auth structs exhaustively (no `..`), so a new field fails to compile until someone decides whether it may travel; the import side drops secrets, key files, local profiles and key paths from a shared archive again, because an archive is untrusted input.
- `SecretBackend` (`fbterm-secrets`) is the one `SecretStore` the app uses. Auto probes the system storage lazily, on the first data call (never at launch, so users who never save a secret see no OS prompt) and switches to the vault only for a storage that is missing altogether (a denied, locked or failing one never switches: it would strand the secrets). The UI reads lock-free mirrors (`storage()`, `vault_unlocked()`, `vault_exists()`, `needs_main_password()`); every call that can touch the vault (scrypt, whole-file rewrite) runs on the blocking pool, never on the UI thread, and prompts reach the user through `Prompter` (`unlock_vault`, `set_vault_password`, `ask_key_file`; `NoPrompt` implementors answer None, which reads as not saved).
- `age` derives its scrypt work factor per build: a debug build cannot open archives or vaults made by a release build (age refuses the larger work factor), and the other way round is fine.

### Hardware checks (only on real machines; not covered by CI)

Linux (GNOME and KDE, each on Wayland and X11):
- Drag the empty tab bar to move, double-click to maximize and restore, resize from every edge and corner; a normal click on the bar or a tab never triggers the Title bar fallback.
- On a compositor that refuses moves, the fallback switches that session to the system title bar and shows `This desktop doesn't let fbterm move its window, so the system title bar is used. Change it in Settings.` once; choosing fbterm under Title bar tries again. Also check no false fallback after a grab where the pointer leaves and re-enters the window.
- Control order and side follow the GNOME `button-layout` and KDE `kwinrc` button settings.
- KDE Plasma on Wayland: blur shows through at `background_opacity` below 1.0 (the detection is a Wayland + KDE heuristic); elsewhere the Settings blur switch is disabled with `Not supported on this system`.

Windows 11:
- Acrylic blur shows through on build 22621 or newer, and the switch is disabled on older builds.
- The SmartScreen prompt on the unsigned `.msi` (`More info`, `Run anyway`).
- Start menu and Add/Remove Programs icons.
- Upgrade from an older `.msi` replaces it and keeps `%APPDATA%\featherbit\fbterm\config`.
- A local shell starts from the Start menu shortcut (no console window flashes).
- Drag, resize, maximize and restore, and the caption buttons' hover and pressed states.
