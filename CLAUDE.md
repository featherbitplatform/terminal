# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**featherbit terminal** (also *featherbiterminal*), binary `fbterm`: a native, SSH-first terminal emulator in Rust with an **iced** GUI. Built to stay fast and light with ~20 concurrent sessions (streaming logs, idle shells, AI-agent TUIs), with saved SSH profiles, jump hosts, a quick-launch palette, tabs and tiling, named tunnels, an SFTP file panel and encrypted profile export. Also a plain terminal for local shells.

Binding design: `docs/superpowers/specs/2026-10-23-featherbit-terminal-design.md`. Read it before any feature work; it records which decisions are the owner's and which are open builder's calls. Implementation plans go next to it under `docs/superpowers/plans/`.

## Rules specific to this repo

- **Describe the product only on its own terms.** Never name or compare to another terminal application anywhere committed to this repo: code, comments, docs, website, commit messages, PR text, this file.
- **Cross-platform code, macOS releases first.** Code must build and test on macOS, Linux and Windows (CI covers all three); platform-specific APIs only behind `cfg` with an alternative. Release artifacts are unsigned (macOS `.dmg` for Apple Silicon + Intel, Linux `.deb`/`.rpm`/`.tar.gz`, Windows `.msi`) until signing is decided.
- **Secrets never go in config files.** Passwords and key passphrases live in the system storage (macOS and Linux: a single OS-keychain item, a map keyed by profile id, via the `keyring` crate; Windows: the DPAPI-encrypted file `secrets.dpapi`) or in the `age`-encrypted vault `secrets.fbvault`, chosen by the `secret_storage` setting; config is TOML in the platform config dir.
- **No home-grown crypto.** Export archives (`.fbprofiles`) use `age` with a passphrase recipient. "Shared" exports strip passwords, passphrases and key paths.
- **Host keys:** `~/.ssh/known_hosts` shared with OpenSSH; trust-on-first-use prompt for unknown hosts; changed keys are refused, never auto-accepted.
- **Look and feel** follows the workspace design system v2 "Graphite" (`../design-system-v2/`, start at its `SKILL.md`): dark-first graphite (the default look: the Graphite scheme gives the chrome exactly these colors; every other global color scheme recolors the chrome from its own colors, so the accent is the global scheme's and violet is Graphite's own, owner's decision 2026-11-09), Geist Mono for real values, Lucide icons, no emoji or em-dashes in product copy.

## Architecture (from the design)

- **Emulation:** `feathercritty` (our Apache-2.0 fork of the upstream emulation crate, [github.com/featherbitplatform/feathercritty](https://github.com/featherbitplatform/feathercritty)) owns parsing, grid and scrollback per session. Local shells via `portable-pty`.
- **Rendering:** custom iced widget drawing from a glyph atlas with damage tracking; invisible tabs do no render work. If iced primitives are too slow, the approved fallback is a raw wgpu renderer for the grid inside the iced window — iced stays for all chrome. Switching GUI toolkit is not an option without the owner.
- **SSH:** in-process `russh`, never shelling out to system `ssh`. Auth in scope: password, private key (± passphrase), ssh-agent; 2FA, FIDO keys, certificates and agent forwarding are deferred.
- **Connection model:** one SSH connection per profile, shared like ControlMaster. Every tab/pane is a shell channel on it; the file panel (SFTP via `russh-sftp`) and tunnels are further channels. Tunnels belong to the connection, not to a tab: `with-shell` tunnels start when the profile's first shell connects and stop with its last, on-demand tunnels may open a shell-less background connection, and the connection closes only when its last channel does.
- **Jump hosts:** a profile's jump chain references other saved profiles; each hop is SSH over a `direct-tcpip` channel from the previous hop, authenticated with that hop's own profile.
- **Runtime:** one process, tokio for I/O, one task per session feeding its terminal; background sessions keep parsing but never render. Multi-window (iced daemon mode); windows, tabs and pane layout restore on relaunch (the Profiles, Settings, Color schemes and Welcome page tabs are not restored, and cannot be split or merged), reconnecting as built: every pane of each window's visible tab at once, background tabs on first show.
- **Palette:** Cmd+Shift+P (Ctrl+Shift+P elsewhere), application-scoped, fuzzy (`nucleo`) over profiles first, then tunnels (choosing one switches it on or off), then app actions.
- **Shortcuts:** actions, chords, per-platform defaults and the binding table are data in `fbterm-config/src/keys.rs`; the user's overrides are the `[keys]` table of `settings.toml`. The app keeps one `Bindings` (`App::bindings`, rebuilt when settings apply) and matches presses against it in `keys.rs`/`shortcuts.rs`; tooltips, the palette and the Settings tab's Keyboard section read the same table, so never hardcode a chord label.

## Conventions

- **Gitflow:** `main` holds tagged releases (`vX.Y.Z`) only; `develop` is the integration branch; work on `feature/<name>` off `develop`; `release/X.Y.Z` and `hotfix/<name>` as in the gateway repo.
- **Conventional Commits** (`feat:`, `fix:`, `docs:`, `ci:`, `chore:`, `refactor:`, `test:`, optional scope). Do not add a `Co-Authored-By` trailer.
- **Semantic versioning**, released like the gateway: `release/X.Y.Z` off `develop` (version bump in `Cargo.toml` there), merged into `main` with an annotated `vX.Y.Z` tag, then merged back into `develop`. The `v*` tag triggers the release workflow.
- Docs website: Docusaurus in `website/`, deployed to `https://featherbitplatform.github.io/terminal/` by `.github/workflows/docs.yml` — same pattern as `../gateway/website`.
- **Changelog:** `CHANGELOG.md` at the root (Keep a Changelog: one `## [X.Y.Z] - date` section per version with Added/Changed/Fixed lists, each line ending in its PR link, and a release link at the bottom). The release branch adds the version's section with the bump. The docs site shows it as the Changelog page: `website/scripts/changelog.mjs` copies it to `website/docs/changelog.md` (git-ignored) before `npm start` and `npm run build`; never edit the copy.
- CI gates: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `cargo deny check`, plus the security scans in `.github/workflows/security.yml` (semgrep, cargo-deny, grype, gitleaks over the full history, npm audit of `website/`; also weekly on `main`). Their configs live at the repo root (`.semgrepignore`, `.gitleaks.toml`, `.grype.yaml`, `deny.toml`, `website/audit-ci.jsonc`); every ignore carries a one-line reason. Releases attach CycloneDX SBOMs (`fbterm-<version>.cdx.json`, `fbterm-docs-<version>.cdx.json`, syft pinned in `release.yml` and `dev/sast.sh`).

### Debug aids (environment variables)

- Always available: `FBTERM_CONFIG_DIR=<dir>` (use this directory instead of the real config), `FBTERM_SECRETS=memory` (never touch the OS keychain), and the release-build measurement flags `--perf-tabs <N>` (or `--perf-panes <N>`: one tab with N panes) `--perf-cmd <cmd> [--perf-exit-after <secs>] [--perf-close-after <secs>]` (the last closes every tab but the active one).
- Always available, for keyboard reports: `FBTERM_LOG_KEYS=1` (read once at startup, `key_log.rs`) logs at INFO, while the Settings tab records a shortcut and only then, one line per keyboard event (`KeyPressed`, `KeyReleased`, `ModifiersChanged`) in any window: key, modified key, physical key, location, modifiers, repeat, the typed text and character keys (recording window only; elsewhere named keys and physical keys) and whether it was captured. Each event is logged by the window-level listener (`listener`: did the window get it at all, and did a widget capture it) and by each `Shortcuts` wrapper it reaches (`shortcuts`: captured before the wrapper saw it). Windows release builds have no console, so send stderr to a file from PowerShell: `$env:FBTERM_LOG_KEYS=1; Start-Process "C:\Program Files\featherbit terminal\fbterm.exe" -RedirectStandardError "$env:TEMP\fbterm-keys.log" -Wait`, record the shortcut in Settings, quit fbterm, then read `$env:TEMP\fbterm-keys.log`.
- Debug builds only (ignored in release): `FBTERM_OPEN_TABS=<profile>,<profile>`, `FBTERM_SPLITS=<layout>` (the first tab as split panes of these profiles: `|` side by side, `/` stacked, binding left to right, e.g. `A|B/C`), `FBTERM_PALETTE_QUERY=<text>`, `FBTERM_SCREENSHOT=<path.png>` (capture the first window and exit), `FBTERM_SCREENSHOT_WINDOW=editor|settings|schemes|archive` (`editor`, `settings` and `schemes` capture the terminal window whose tab shows that page; combine with `FBTERM_OPEN_EDITOR`/`FBTERM_OPEN_SETTINGS`/`FBTERM_OPEN_SCHEMES`), `FBTERM_OPEN_EDITOR=<profile>` (the Profiles tab in the first window, that profile selected), `FBTERM_OPEN_SETTINGS=1` (the Settings tab in the first window; `secrets`: scrolled to the Saved secrets section), `FBTERM_DEMO_VAULT=1` (with `FBTERM_SECRETS=memory`: makes the in-memory backend's temporary vault, main password `demo`, so Settings shows `Reset vault`; a screenshot waits for it), `FBTERM_OPEN_SCHEMES=1` (the Color schemes tab in the first window; any other value selects the scheme of that name; with `FBTERM_DEMO_GALLERY=1` it shows the theme gallery with a sample catalog, one theme per row kind plus a worst-case row with a very long name and credit, never fetched, its installed ones written first to `schemes/` only when `FBTERM_CONFIG_DIR` is set and non-empty; `FBTERM_DEMO_GALLERY=question` also asks about updating the sample theme `Meadow` as edited on this machine), `FBTERM_OPEN_TUNNELS=1` (the first window's tunnels panel open), `FBTERM_TAB_BAR=left` (start with tabs down the left side, writing nothing), `FBTERM_OPEN_WELCOME=1` (the Welcome tab open in the first window, due or not), `FBTERM_OPEN_ARCHIVE=export|import` (the export and import window in that mode; with `FBTERM_DEMO_ARCHIVE=1` export starts with jump hosts unchecked and key files on, and import shows a sample archive built in memory, its key folder in the temporary folder), `FBTERM_DEMO_FILES=<folder>:<item>,<item>,...` (the first window's file panel open on a sample listing served for every SSH pane and folder, connected or not, never touching the network, with a sample transfer queue (a running and a finished download of the first files and a failed in-place upload; `Download`, `Upload…` and `Retry` there add rows that stay at their start); an item is `name`, `name/` for a folder or `name -> target` for a link (target ending in `/`: a folder), optionally followed by `|<bytes>|<YYYY-MM-DDTHH:MM>`), `FBTERM_DEMO_UPLOAD=<name>,<name>` (with `FBTERM_DEMO_FILES`: upload these names into the first listing shown, raising the clash dialog for names it has), `FBTERM_DEMO_PROMPT=hostkey|password|keyfile|changed|unlock|setpassword` (`setpassword` only with `FBTERM_SECRETS=memory`), `FBTERM_DEMO_UPDATE=<version>` (with `check_updates = true`: the update check reports that version as the latest release without any network access, so the tab bar's settings dot and the Settings line show), `FBTERM_DEMO_TOOLTIP=new|profiles|tunnels|files|settings|close` (keep that tab-bar tooltip showing; `files` only while the files button shows, e.g. with `FBTERM_DEMO_FILES`), `FBTERM_FIND=<text>` / `FBTERM_FIND_ALL=<text>` (open the active tab's find bar or the find-in-all-tabs box with that query, about a second after startup), `FBTERM_DEMO_RENAME=<text>` (the rename field on the first window's active tab holding that text, about a second after startup; a screenshot waits for it), `FBTERM_SCALE=<factor>` (extra UI scale on top of the OS's, e.g. `0.625` on a 2x screen for a fractional 1.25), `FBTERM_DEMO_CHROME=windows|linux[:<button-layout>]` (draw that system's window controls on any system, Linux with an optional GNOME `button-layout` value, e.g. `linux:close,minimize,maximize:`), `FBTERM_DEMO_BLUR=<material>[+fill][:<alpha>]` (macOS, with `macos_blur_style = "classic"`: replaces classic's blur view material, by a name from `chrome::BlurMaterial::NAMED` such as `header-view` or `hud-window`, and its alpha, above 0 and at most 1; the fill stays hidden unless `+fill`; the scheme's appearance stays; candidates in `dev/blur/README.md`), `FBTERM_DEMO_BLUR_DUMP=1` (macOS: the first blurred window logs, once, the layer tree of an unmodified system blur view (a temporary one, removed after) for every material in both appearances, then its own blur view's tree as used; findings in `dev/blur/README.md`). Runs with `FBTERM_OPEN_TABS`, `FBTERM_SPLITS` or `FBTERM_SCREENSHOT` never write `state.toml`.
- Always on, in the config dir (`crash.rs`, paths in `fbterm-config/src/paths.rs`): `fbterm.log` gets every log line stderr shows (INFO, no colors; libraries logging through the `log` crate, iced and wgpu, arrive through `tracing-log`'s bridge, so it names the graphics adapter, backend, surface format and alpha mode iced picked; `iced_winit` is held at WARN because it dumps every window's attributes, title included), and each start first moves the last run's log to `fbterm.previous.log`. A panic (hook installed first thing in `main`, after `--version`; the default hook still prints to stderr) or `daemon.run()` failing appends a report (UTC time, version, OS and arch, thread, message and location, backtrace) to `crash.log`, moved to `crash.previous.log` before an append once it is over 256 KiB; a failed start also shows a message box on Windows. A panic whose message `crash::Cause` recognizes (`Parent device is lost`: wgpu panics while presenting on a lost GPU device, which iced cannot recover from) gets a `hint:` line, and its marker holds the cause (`gpu-lost`), so the banner says the graphics device was lost and to update the driver or set `WGPU_BACKEND`. Each report creates the marker `crash.pending` (empty, or the cause), which the next launch removes, showing `fbterm ran into an error last time. The report is in <crash.log>.` once in the window banner; runs that never write `state.toml` leave the marker alone.
- Rule for agents: look at the app only through its own-window screenshots (`FBTERM_SCREENSHOT`), never full-screen capture. Combine with `FBTERM_CONFIG_DIR` and `FBTERM_SECRETS=memory` so a run cannot touch real profiles or secrets.

## Gotchas learned

- Windows CI clippy fails on imports and helpers used only by `#[cfg(unix)]` tests; gate them with the same `cfg`.
- Linux packages are built in an `almalinux:9` container (glibc 2.34, RHEL 9's), not Debian 12: a Debian 12 build links `hypotf@GLIBC_2.35` and the `.rpm` then refuses to install on RHEL 9. `dev/package-linux.sh` refuses a binary that needs a glibc symbol newer than 2.34. The binary links only glibc and libgcc; winit, wgpu and rfd open the rest at run time (list in the `[package.metadata.deb]` comment of `crates/fbterm/Cargo.toml`); recheck with `strings` on the release binary after dependency upgrades.
- Windows release builds are GUI-subsystem programs (`windows_subsystem` in `main.rs`, release only), so no console window opens beside the app; their stdout reaches only a pipe or file (`fbterm --version | more`), and any child process they start needs `CREATE_NO_WINDOW` or it flashes a console. `build.rs` embeds the icon and version information with `winresource` (Windows hosts only). The `.msi` (`crates/fbterm/wix/main.wxs`) keeps one UpgradeCode forever; never change it.
- Window chrome is `Chrome` in `crates/fbterm/src/chrome.rs`: `Unified` on macOS (never changed), `Drawn` on Windows and, by default, Linux (no OS decorations; the tab bar holds drawn controls, moves and resizes through iced's `drag_window`/`drag_resize`), `Native` only on Linux. It lives in a switchable `ChromeCell`: the `window_decorations` setting and the fallback (`move_watch.rs`: a move or resize the desktop ignores, detected once per session, sets `chrome_fell_back` and shows `FALLBACK_NOTICE`; the setting itself stays `"fbterm"`) toggle decorations on open windows. Never treat an ordinary click as a move request, or the fallback fires falsely. The Settings blur row asks `chrome::blur_here()` (Windows build >= 22621 via `reg query`, Linux Wayland + KDE, macOS always).
- macOS 26 and later draw the current window design (the larger corner radius that `chrome::system_corners` asks for among it) only for an app built against the macOS 26 SDK or newer; a binary recording an older SDK keeps the old look whatever it does. The release job selects the newest Xcode 26+ on the runner, and `dev/package-macos.sh` refuses an app whose binary records an older SDK (`dev/macos-sdk.sh`, tested by `dev/test-macos-sdk.sh`). Check a build with `otool -l <binary> | grep -A4 LC_BUILD_VERSION`. 0.7.0 through 0.8.1 shipped built against SDK 15.5, so their corners stayed small on macOS 26+ although local builds looked right. Blur needs the same care: the window library blurs on macOS through the private `CGSSetWindowBackgroundBlurRadius`, which keeps the pre-26 window shape and shrinks a blurred window's corners, so macOS windows never ask it for blur (`Chrome::window_blur`); `chrome::system_backdrop` puts an `NSVisualEffectView` (behind-window blending, identifier `fbterm.blur`) under the content view inside the frame view instead, clipped by the window's own corner mask. Its material, appearance, alpha and fill are a `chrome::BlurLook` from `chrome::blur_look` for the `macos_blur_style` setting: `native` = `BlurLook::NATIVE` on the plain system view (under-window-background, inherited appearance, alpha 1, fill kept: exactly what 0.8.3 shipped), `classic` = `clear`: the `FbtermClearBlurView` subclass (`blur_layers.rs`) with the titlebar material, every layer but the blurring backdrop hidden (found by its blur filter, `blur_layers::layers_to_hide`; re-hidden, inside a `CATransaction` with actions off, after layout, layer updates, appearance and backing changes and every re-tune, since the view rebuilds its layers; an unexpected tree, found by a tune or by any of those hooks, falls back to the hud-window material with one log line, and the view then leaves that material's layers as drawn until the next re-tune), in the dark or light appearance of the scheme of the active tab's first pane (the layout's top-left tile, `Layout::first_pane`; `schemes::is_dark`, via `App::scheme_for`), so the terminal background at `background_opacity` is the only tint. A change of `clear` removes the view and adds a new one of the other kind. `App::blur_views` remembers each blur view's look; `sync_blur_views` (post-update hook, `blur_style.rs`) re-tunes changed ones in place through `chrome::retune_blur` (found again by identifier), so a style or scheme change applies to open windows at once.
- `hdiutil create` fails locally on macOS 27 ("Resource busy"); `dev/package-macos.sh` falls back to `diskutil image create` locally, CI uses `hdiutil` only.
- Redraw contract: call `take_dirty` before locking the terminal to draw; hidden tabs, and every tab of a window that cannot be seen (`visibility.rs`), leave `Dirty` pending until they are shown. Every message redraws every window, so output `Dirty` is paced before it reaches the update loop (`pacing.rs`, at most `max_fps` per second: the setting, default `OUTPUT_FPS` = 60, or the fastest display with `"display"` via `display_rate.rs`; read live from the shared `OutputRate`); never add a periodic subscription or redraw loop that keeps running without new output or input (debug aids aside).
- `winit` comes from our fork `featherbitplatform/winit` (branch `fbterm/v0.30.13`, a GitHub fork of upstream; changes listed in its `FORK.md`) through `[patch.crates-io]` pinned by `rev` in the root `Cargo.toml`, so iced uses it unchanged otherwise. Its one change is a backport of upstream's Windows 11 fix (`488c036`, rust-windowing/winit#4041, not in any 0.30 release): `WM_DPICHANGED` applies the rect Windows suggests except on Windows 10 builds before 22000 (winit's own placement threw windows away from the cursor, or off-screen, between monitors of different scale). Drop the fork once iced moves to a winit release with it. Change it in the fork's branch, push, then bump the `rev`; never open anything against upstream winit unless the owner asks.
- `feathercritty` is a git dependency pinned by `rev` in the root `Cargo.toml` (its changes from upstream are listed in its README; `deny.toml` allows git sources from `github.com/featherbitplatform` only). To change emulation code: commit in the feathercritty repo (`../feathercritty`, Conventional Commits, notice line at the top of each file it modifies), push, wait for its CI, then bump the `rev` here and run the checks. For local development, point Cargo at the working copy with a `[patch."https://github.com/featherbitplatform/feathercritty"]` entry `feathercritty = { path = "../feathercritty" }` in the root `Cargo.toml`; never commit it.
- feathercritty stores scrollback in a compact byte form, so `grid[...]` indexing is screen-only: use `grid.screen()[...]` for the visible rows and `grid.screen_mut()` to write them. History rows are read through `RowReader`, `Grid::cell`, `Grid::wraps` and `Grid::is_clear` (see the feathercritty README, "Compact history"); never index a history line directly.
- Search positions are `StablePoint`s (`fbterm-term/src/search.rs`): stable line = feathercritty's `Grid::scrolled_lines()` + grid line, unchanged while output scrolls; a resize (reflow) or a screen switch invalidates them, so the find bar searches again then.
- Tabs on the left (`tab_bar = "left"`, `Settings::tabs_left`): `tab_sidebar.rs` draws the column beside the content at the window's chosen width (`App::sidebar_widths`, default `SIDEBAR_WIDTH` 220, clamped 140..=480 by `clamp_sidebar_width`, saved per window as `SavedWindow.sidebar_width` only when not the default; a new window starts at the default), yielding in a narrow window so the terminal keeps `MIN_TERMINAL_WIDTH`; the rule at its right edge is the drag handle (`sidebar_resize.rs`: the pure `resize_event` over the rule plus 4 px of the content, never over the list's scrollbar, reporting `TabBarMsg::SidebarResize` per move and `SidebarResizeEnd` on release, double-click resets, the rule draws in the accent while dragged); a row whose title is wider than `label_width` gets its whole title as a `tip`, never while a drag, a carry or a modal is on (`Sidebar::tips`). With `tab_groups` on (`Settings::tab_groups_on`, only with tabs on the left), `tab_groups.rs` keeps each window's tab order grouped (`App::regroup_all` in the post-update hook, a stable sort by `Group`: `Featherbit` for page tabs, named groups case-insensitive, `Other` last), the sidebar draws headers between rows (`Item`, `items`, `item_tops`; a header's `Space` is `HEADER_GAP - ROW_SPACING` tall because the column's spacing lies on both sides of it), collapsed group keys live per window (`App::collapsed`, `SavedWindow.collapsed_groups`, `TabBarMsg::ToggleGroup(section index)`), the active tab's group unfolds when the active tab changes (`expand_active`, so folding the active group by hand sticks), `NextTab`/`PrevTab`/`SelectTab` go through `App::travel_tabs` over `visible_rows` (`WindowState::select_number` is gone), and drags are kept in the group through `Strip::range`/`clamp` with `Strip::indices` mapping rows to window indices (the bar passes the identity map). The bar then lists no tabs and paints plain, and the content outline starts at the column's rule (`TabBar::outline_start`). The press, drag, gap and right-click logic of the bar and the column is one axis-generic helper (`tab_drag.rs`: a tab dragged along its own strip and let go in a gap moves there, `DragMsg::ReorderTab`, with the same violet marker a carried tile gets); the sidebar's rows live inside a scrollable, so their coordinates are shifted by the scroll offset (`Strip::scroll`), which `TabBarMsg::Scrolled` keeps current, and `App::reveal_active_tabs` (after every update) scrolls a newly active tab into view. The right-click menu on a tab (`tab_menu.rs`: `Copy password` for a password SSH profile's tab, `Close tab`) shares `context_menu.rs` (one `ContextMenu` with a `MenuTarget` and an item list); its items show a chord (from `App::bindings`) only on the active tab, where the key does the same thing, and `Close tab` only when the tab has one pane; the `Copy password` action (`copy_password`, Cmd+Shift+K / Ctrl+Shift+K) copies the active tab's; the password is read on the blocking pool as a `Zeroizing<String>`, never logged, and cleared from the clipboard after `CLEAR_AFTER` if still there (one task with a sleep, never a tick).
- Ended sessions (`reconnect.rs`): a pane whose session ended (`Disconnected`, `Exited`; never `NotConnected`, `Connecting` or `Connected`) shows `App::ended_bar` below its terminal in `pane_view` (a column, never an overlay, so the last output stays readable; one clipped line from `bar_text`, the `Reconnect` chord and a `Reconnect` button for an SSH profile or `Restart` for a local one, `Message::Revive(wid, pane)` for that pane only). The `reconnect` action (Cmd+Shift+O / Ctrl+Shift+O) and the tab menu's `Reconnect`/`Restart` item (`MenuItem::revive`, shown only when `App::revive_kind` finds an ended pane, first in the menu) bring back every ended pane of the tab through `App::revive_pane`, which checks the state again, so a stale click or key never restarts a live session. Enter on such a pane still goes through `tabs::route_input` (which also starts `NotConnected` panes). A deleted profile's pane offers no button.
- The tab bar paints its background around the active tab only (`BarBackground` in `window.rs`: rectangles plus concave top-corner pieces and bottom flares drawn as clipped disc and ring quads, all in whole physical pixels from `App::physical_scale`; it also paints the inactive tabs' hover and tint), so a translucent bar never lies under the active tab; anything drawn behind it would double the alpha. It also always draws the content outline (`outline`): a line in the border color along the content's top and around the active tab (corners and flares), always outside the tab, one logical pixel in whole physical pixels; with a panel docked it ends at the panel's left rule (x from `docked_width`), which carries it down, else at the window's right edge. The drawn controls' plate is drawn after the background, so the controls stop one outline width above the bar's bottom and the strip under them paints the outline color only when the outline reaches the window's edge (`TabBar::outline_to_edge`, no panel docked); with a panel docked the strip keeps the bar color, flush with the panel. Tab colors (stripe or whole-tab tint, contrast-picked text) come from `tab_look.rs`.
- Hairlines (`ui::hairline(scale)`: one logical pixel rounded to whole physical pixels, at least one) take the window's `App::physical_scale`, which is kept for every open window (`os_scales`, read on `AnyWindowOpened` and on `Rescaled`), not only terminal ones: a one-logical-pixel rule at a fractional scale lands between pixels and shows as two. Surfaces that touch (the window header, the panels' left rule, the editor's and the Color schemes tab's sidebar and footer) draw one `ui::horizontal_rule` or `ui::vertical_rule` (snapped hairlines) on one side each, never a `Border` all around: two bordered containers side by side add up to a two-pixel line where they meet.
- Tab export (`fbterm-term/src/export.rs`, `fbterm/src/export.rs`) streams the history on the blocking pool in 1000-row chunks, locking the terminal per chunk and addressing rows by stable line (like search), into a temporary file renamed at the end; with the alternate screen up it reads the normal grid through feathercritty's `Term::inactive_grid()`.
- A session can continue into an existing `SharedTerminal` (`spawn_local_into`, `open_shell_into`), which is how reconnect keeps scrollback.
- Freed scrollback goes back to the OS through `memory::release_freed()` (macOS `malloc_zone_pressure_relief`, glibc `malloc_trim`, nothing elsewhere; at most once per 5 s, on the blocking pool). Only user actions call it (closing a tab or window, requested when the closed session task reports `SessionEvent::Released` after dropping its terminal, which only a user close triggers; lowering `scrollback_lines`); a program's own history clear (`CSI 3 J`, `RIS`) must never, because remote programs cause no host work. Lowering `scrollback_lines` applies to every open tab through `Terminal::set_scrollback`; `apply_settings` takes a `SettingsSource` (`File` sets the settings notice, `Window` does not).
- Tunnels share the pooled SSH connection of their profile (`SshPool::acquire`); the tunnel runtime claims its forward exclusively (`claim_forward`), and a restart must `stop_and_wait` first so the port is released. The client handler (`ssh/mod.rs`) refuses every server-opened channel unless it is a `forwarded-tcpip` for a remote forward registered on that connection, and always on hop connections: a remote program must never open, change or close a tunnel. A pooled connection is handed out only on the profile's current route (the SSH settings of the profile and its jump chain), so an edit makes the next caller dial afresh while running tunnels keep the old one. The raw remote-forward calls on `Connection` exist only with the crate's `test-support` feature, for the live tests.
- File panel transfers hold their own `Arc<Sftp>` and belong to the connection, not to a panel or window: hiding the panel never cancels them, and the app never cancels them implicitly (only the user's `Cancel`, or `Cancel transfers and close` in the close or quit confirmation in `prompts.rs`/`file_panel/queue.rs`). Nothing is ever written half-done under a real name: downloads and uploads go to `.<name>.fbterm-part` and are renamed on completion (removed on cancel or failure); a Replace upload uses the part file plus `posix-rename@openssh.com` and falls back to an in-place write (`Replaced in place`, `File may be incomplete.` on failure). Two downloads never share a destination (`same_destination`, case-insensitive), and `Download` (`DownloadMode::FreeName`) never replaces a file that appeared meanwhile (hard link to the final name, else the next free name). Every upload starts through `launch_job` in `queue.rs`, which refuses a second upload of a name already uploading into that folder. Server names use one unsafe-character set on both sides (`transfer::is_unsafe_char`: shown as `?`, written locally as `_`). A remote program must never start a transfer or open the panel.
- After an SSH shell connects, `App::check_sftp` (`file_panel/mod.rs`) opens the profile's SFTP session in the background on the live connection only (`SshPool::existing` / `Sftp::open_existing`, `Backend::check`: no prompter, never dials), for the tab bar's files button (`App::files_button`, shown while the focused pane's profile has a working session). A checked session lives like a panel's: kept while the profile has a connected shell, a panel shows it or a transfer runs, released in `sync_file_panels` otherwise, so it never keeps a connection open by itself. A refusal (`Listing::Unavailable`) is forgotten with the profile's last shell, so a reconnect checks again; a panel shown during a check (`Listing::Checking`) replaces it with its own open, which may ask.
- Color scheme resolution: profile override, then global `color_scheme`, then Graphite, always through `App::scheme_for` (never read a pane's colors elsewhere). After scheme files change call `App::reload_schemes`; after a setting or profile change `schemes_moved` recolors the affected panes (`reapply_schemes`). Chrome follows the global scheme (spec `docs/superpowers/specs/2026-11-09-schemes-tab-and-themed-chrome-design.md`): `theme::tokens_for(&Scheme)` derives the chrome tokens (interned, so repeated calls leak nothing; Graphite and Graphite Light keep today's exact colors, `terminal` is the scheme's background) and `chrome_theme` wraps them; `App::chrome_scheme` is the global scheme and `App::retheme` re-derives the tokens, called from `App::new`, `apply_settings` and `reload_schemes` (never set tokens elsewhere); a profile's scheme never touches the chrome. Text on a tab or button uses `tab_look::ink(t, bg, role)`, which checks the role actually drawn. The `theme` setting is gone (a stale key logs `theme is no longer used: ...` and the next settings write drops it). Scheme notices (unreadable files, missing ids) go to the window banner via `refresh_scheme_notices`, once per distinct line. Pane accent borders draw only in tabs with more than one pane.
- Theme gallery (Color schemes tab, Gallery view): the catalog (`catalog.toml` in `featherbitplatform/terminal-themes`, `catalog::CATALOG_URL`, parsed by `fbterm-config/src/catalog.rs` with size and field caps) and every theme in it are untrusted input. It is fetched only on a user action (showing the Gallery tab while no catalog has loaded in this run, so the first time and again after a failure; `Refresh`; `Retry`), through `net::get` on the blocking pool, never at startup, in the background or from a remote program, and nothing is cached on disk. An installed theme is a normal scheme file `gallery-<id>.toml` with two optional tables. `[credit]`: project, author, url, license, copyright, license_file, description, derived. `[gallery]`: id (the catalog id), version, colors_hash (`schemes::install_hash`: `2:` plus FNV-1a of the name, font family and size and the 20 colors as installed; a mismatch, a hash of another format, or no block on a `gallery-` id, means edited). `sanitize_gallery` drops a `[gallery]` block whose id does not match the scheme id on every load; imports (window file import, profile archives) drop `[gallery]` always, so an imported gallery theme counts as edited. `[credit]` text follows one character rule everywhere (`schemes::is_unsafe_char`/`credit_is_safe`): a catalog theme breaking it is skipped, an unsafe `[credit]` in a scheme file or archive is dropped (`sanitize_credit`). A catalog whose every theme was skipped is a failure line. Update replaces the file in place unless the scheme is edited (then `Replace my changes / Install as a copy / Cancel`, Enter = copy). Duplicate and Install as a copy keep `[credit]` and drop `[gallery]`; single-file and profile-archive exports keep `[credit]` and strip `[gallery]` (local bookkeeping). Gallery themes are not part of fbterm: their licenses stay in their files and in `terminal-themes` (`LICENSES.md`).
- Suggested fonts (spec `docs/superpowers/specs/2026-11-09-theme-fonts-design.md`): a scheme's optional `[suggested_font]` (family, https url, allow-listed license; `schemes::suggested_font_from`/`suggested_font_problem`, the credit character rule, 2000-char caps) is read leniently (`FontSlot`): a bad table is dropped with a banner line (`read_file_noted`, catalog `notes`), never the scheme. It travels like `[credit]` (install, update, duplicate, exports, archives) and is not in `install_hash`. Built-ins carry one in code. Pane font = scheme `font_family`, else (with `use_theme_fonts`) the installed suggestion, else the global font: `schemes::theme_font` through `App::scheme_font` (`theme_fonts.rs`), used by `pane_style`, the Color schemes preview and ligature warming. The resolved font is cached per scheme (`App::scheme_fonts`, rebuilt by `rebuild_scheme_fonts` after schemes, installed list or settings change). "Installed" is `App::installed_fonts` (sorted), read through `App::font_io.list` from the renderer's font db (monospaced faces plus any suggested family, flag or not; bundled Geist Mono always counts). The db reads system fonts once at startup, so on a user action only (the Color schemes tab shown or its window focused (`App::schemes_shown`), `ShowGallery(true)`, a catalog loaded, `use_theme_fonts` turned on) and only while a suggested family is missing, `App::scan_fonts` rescans the system with a fresh `fontdb` on the blocking pool and adds to the renderer just the files of the closest regular, bold, italic and bold italic faces of each missing suggested family (`pick_new_faces`: slant, then normal width, then weight), memory-mapped through `raw().db_mut().load_font_file` (clears cosmic-text's match cache), then bumps `fbterm_term::fonts_loaded` so every terminal view re-measures and drops its shaped text (a pane naming that family stops using fallback metrics); a scan asked for during a scan queues one follow-up (`fonts_rescan`); opening the Settings font list (`SettingsMsg::FontsOpened`, pick list `on_open`) scans the same way for every monospace family the renderer lacks (`ScanFor::monospace`, `App::scan_monospace_fonts`), and every finished scan refreshes an open Settings tab's list from `FontIo::monospace`; never `load_system_fonts` on the renderer, never per frame or on `Select`. `catalog::status` re-offers Update for an unedited theme at the same version whose `[suggested_font]` differs (themes written by an fbterm that dropped the table). `Download (<host>)` opens the page through `GalleryIo::open` (user click); the url must pass `schemes::is_plain_https_url` (plain host name and port, no userinfo, `%`, backslash or brackets) both at validation and on open, and a long host is cut from the left but always keeps its owner labels, two, or three under a two-label public suffix like `github.io` (`theme_fonts::host_label`; the whole host when those do not fit). `FontIo::loaded` (default `fbterm_term::fonts_loaded`) is replaced in tests, which never assert on the process-global font epoch; fbterm never downloads fonts.

- Shared archives are stripped by construction: `archive_build::shared_copy` destructures the profile and its SSH and auth structs exhaustively (no `..`), so a new field fails to compile until someone decides whether it may travel; the import side drops secrets, key files, local profiles and key paths from a shared archive again, because an archive is untrusted input.
- `SecretBackend` (`fbterm-secrets`) is the one `SecretStore` the app uses. Auto probes the system storage lazily, on the first data call (never at launch, so users who never save a secret see no OS prompt) and switches to the vault only for a storage that is missing altogether (a denied, locked or failing one never switches: it would strand the secrets). The UI reads lock-free mirrors (`storage()`, `vault_unlocked()`, `vault_exists()`, `needs_main_password()`); every call that can touch the vault (scrypt, whole-file rewrite) runs on the blocking pool, never on the UI thread, and prompts reach the user through `Prompter` (`unlock_vault`, `set_vault_password`, `ask_key_file`; `NoPrompt` implementors answer None, which reads as not saved).
- The update check (`update.rs`) and `net.rs` are fbterm's only network access besides SSH, and only by the user's opt-in: `check_updates` (`Option<bool>`, absent = never asked, counts as off) is asked once on the Welcome tab (`crate::welcome`, `App::welcome_due`: opened right after the windows restore when `tab_bar` or `check_updates` is absent and `settings.toml` loads, in runs where `state_saving_enabled` is true, never in unit tests: `App::ask_welcome`; closing the tab writes the defaults for what was not answered). While on, one subscription checks at once and then sleeps 24 h (no tick in between); turning it off drops the subscription and the found version. `net::get` is the shared HTTPS GET (ureq with rustls/ring and bundled webpki roots: no OpenSSL or system library; `https://` only, redirects only to the exact host and port as written, 15 s timeout, size cap); run it on the blocking pool, and reuse it for any further fetch (the theme gallery) instead of adding another client. A remote program must never trigger a check or a fetch.
- `age` derives its scrypt work factor per build: a debug build cannot open archives or vaults made by a release build (age refuses the larger work factor), and the other way round is fine.
